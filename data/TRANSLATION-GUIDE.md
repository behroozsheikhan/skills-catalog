# معیار بازنویسی فارسی

این مرحله «بازنویسی مستقیم از منبع» است، نه اصلاح واژه‌به‌واژهٔ ترجمهٔ گوگل. مخاطب، برنامه‌نویس یا کاربر آشنا با ابزارهای AI است.

## روش

1. فقط متن اصلیِ `what` و `use_when` را مبنا بگیر؛ اگر `what` خالی است، توضیح موجود `description` جداگانه ترجمه می‌شود. ترجمهٔ قبلی مبنای نگارش نیست.
2. ابتدا مشخص کن اسکیل چه کاری انجام می‌دهد، روی چه ابزار یا داده‌ای و با چه هدفی؛ سپس همان معنا را با جمله‌بندی طبیعی فارسی بنویس.
3. اصطلاح جاافتاده را نگه دار: API، CLI، SDK، REPL، tenant، fixture، pipeline و نام محصول‌ها. توضیح کوتاهِ معنای یک اصطلاح زمانی مجاز است که معادل همان مفهوم باشد، نه ادعای قابلیت تازه.
4. دستورها، نام فایل‌ها، identifierها، نسخه‌ها و درخواست‌های نقل‌شدهٔ انگلیسی را تغییر نده.
5. همهٔ اطلاعات واقعیِ متن اصلی، از جمله محدودیت‌ها، مجوز و شرایط استفاده، حفظ شوند. برای کوتاه‌ترکردن متن، قابلیت‌ها یا استثناها را حذف نکن.
6. از فارسی تحت‌اللفظی پرهیز کن: tenant «مستأجر» نیست، linting «پرکردن» نیست و query throughput «مقیاس‌پذیری پرس‌وجو را راهنمایی می‌کند» نیست.
7. فیلد خالی، خالی می‌ماند. بخش قطع‌شده تکمیل نمی‌شود؛ نشانهٔ قطع متن حفظ می‌شود. بدخوانیِ ناشی از قطع واقعی منبع با حدس‌زدن ادامه رفع نمی‌شود.
8. بخش نمونهٔ درخواست یا راهنمای نصب جدید نساز. فقط محتوای موجود را منتقل کن.

## ثبت پیشرفت

- فقط پس از خواندن منبع و نوشتن مجدد هر دو فیلد، روش را `editorial` و نسخه را `editorialVersion: 1` بگذار.
- وضعیت همچنان `draft` است؛ این برچسب به معنی تأیید انسانی نیست.
- `sourceHash` باید با متن اصلی مطابقت داشته باشد. متن‌های کاملاً یکسان با همین hash قابل بازاستفاده‌اند؛ مشابه‌بودن نام کافی نیست.
- ترجمهٔ ماشینی و اصلاحات جزئیِ قدیمی به‌صورت خودکار editorial محسوب نمی‌شوند.
- ابزار ورود ترجمه نباید متن editorial معتبر را با خروجی ماشین جایگزین کند.

گزارش: `npm run translations`

خروجی متن‌های اصلیِ باقیمانده، بدون ترجمهٔ ماشینی قبلی:

```sh
npm run translations -- --editorial-pending --export /tmp/editorial-pending.jsonl
```
